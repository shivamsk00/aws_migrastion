1 Executive Summary कार्यकारी सारांश

The production Node.js backend currently runs on AWS App Runner. This guide describes how to move it to Amazon EC2 (Docker containers behind an Application Load Balancer) without downtime and without touching the existing production data: RDS PostgreSQL, ElastiCache Redis/Valkey, the S3 document bucket and the S3/CloudFront frontend all stay exactly where they are. प्रोडक्शन Node.js बैकएंड अभी AWS App Runner पर चल रहा है। यह गाइड बताती है कि उसे Amazon EC2 (Application Load Balancer के पीछे Docker कंटेनर) पर बिना डाउनटाइम और मौजूदा प्रोडक्शन डेटा को छुए बिना कैसे ले जाएँ: RDS PostgreSQL, ElastiCache Redis/Valkey, S3 डॉक्यूमेंट बकेट और S3/CloudFront फ्रंटएंड जस के तस रहते हैं।

The strategy is parallel running with gradual traffic shifting: App Runner stays live as the instant fallback while EC2 is built, tested and given a small, increasing share of traffic. App Runner is retired only after a stabilisation window with no incidents. रणनीति है पैरेलल रनिंग और धीरे-धीरे ट्रैफ़िक शिफ्ट: EC2 बनाने, टेस्ट करने और थोड़ा-थोड़ा ट्रैफ़िक देने के दौरान App Runner तुरंत फ़ॉलबैक के रूप में चालू रहता है। App Runner को तभी हटाया जाता है जब स्थिरीकरण अवधि बिना किसी घटना के गुज़र जाए।

The three rules that protect production प्रोडक्शन की रक्षा करने वाले तीन नियम
  • Nothing is deleted in the old stack until the rollback window has expired and the owner signed off. कुछ भी डिलीट नहीं होता जब तक रोलबैक विंडो खत्म न हो और ओनर साइन-ऑफ न दे।
  • Both environments share one database, so every schema change must be backward compatible and exactly one environment may run schedulers/background workers at any time. दोनों एनवायरनमेंट एक ही डेटाबेस साझा करते हैं, इसलिए हर स्कीमा बदलाव backward compatible होना चाहिए और किसी भी समय सिर्फ़ एक एनवायरनमेंट schedulers/background workers चलाए।
  • Rolling traffic back does not undo data. Writes already committed stay committed. Rollback is a traffic and code action, not a data action. ट्रैफ़िक वापस करने से डेटा वापस नहीं होता। जो writes commit हो चुकी हैं वे रहती हैं। रोलबैक ट्रैफ़िक और कोड का काम है, डेटा का नहीं।

3 Proposed EC2 Architecture प्रस्तावित EC2 आर्किटेक्चर

EC2 instances in an Auto Scaling group (minimum two, in two Availability Zones) run the Dockerized app under systemd. They sit in private subnets behind a public ALB. Images come from ECR, secrets from Secrets Manager, deployments are pushed by GitHub Actions through Systems Manager (no SSH). Data resources are reused as-is. Auto Scaling group में EC2 instances (कम से कम दो, दो Availability Zones में) systemd के तहत Dockerized ऐप चलाते हैं। वे public ALB के पीछे private subnets में रहते हैं। इमेज ECR से, secrets Secrets Manager से, और deployment GitHub Actions से Systems Manager के ज़रिए (SSH नहीं)। डेटा संसाधन जस के तस दोबारा इस्तेमाल होते हैं।

Network and security design details नेटवर्क और सिक्योरिटी डिज़ाइन का विवरण
  • ALB security group: inbound 443 from the internet (or only the CloudFront managed prefix list if the API is fronted by CloudFront); outbound to the EC2 security group on the app port only. ALB security group: इंटरनेट से inbound 443 (या API CloudFront के पीछे हो तो सिर्फ़ CloudFront managed prefix list); outbound सिर्फ़ app port पर EC2 security group को।
  • EC2 security group: inbound only from the ALB security group on the app port. No port 22. Access via Session Manager. EC2 security group: inbound सिर्फ़ ALB security group से app port पर। पोर्ट 22 नहीं। एक्सेस Session Manager से।
  • RDS and ElastiCache security groups: add one inbound rule each, source = EC2 security group (not a CIDR). Existing App Runner rules stay. RDS और ElastiCache security groups: हर एक में एक inbound rule जोड़ें, source = EC2 security group (CIDR नहीं)। App Runner के मौजूदा rules रहते हैं।
  • EC2 needs a path to AWS APIs: NAT gateway or VPC endpoints (ECR api/dkr, S3 gateway, SSM, ssmmessages, ec2messages, CloudWatch Logs, Secrets Manager). EC2 को AWS APIs तक पहुँच चाहिए: NAT gateway या VPC endpoints (ECR api/dkr, S3 gateway, SSM, ssmmessages, ec2messages, CloudWatch Logs, Secrets Manager)।
  • Hardening: IMDSv2 required, encrypted EBS, no public IP, patched AMI, instance profile with least privilege. Hardening: IMDSv2 अनिवार्य, encrypted EBS, public IP नहीं, patched AMI, least-privilege instance profile।

Honest trade-off ईमानदार ट्रेड-ऑफ़

You are trading managed convenience for control. After migration your team owns OS patching, disk, Docker daemon health and capacity. Plan for that on-call load before committing. आप managed सुविधा के बदले कंट्रोल ले रहे हैं। माइग्रेशन के बाद OS patching, डिस्क, Docker daemon की सेहत और क्षमता आपकी टीम की ज़िम्मेदारी होगी। प्रतिबद्ध होने से पहले इस on-call भार की योजना बनाएँ।

21 PostgreSQL Data Safety PostgreSQL डेटा सुरक्षा

During parallel running both environments write to one database. The schema must work with both code versions at all times, migrations must have one owner, and every write path must be safe if retried or executed by either stack. पैरेलल रनिंग में दोनों एनवायरनमेंट एक डेटाबेस में लिखते हैं। schema हर समय दोनों code versions के साथ काम करे, migrations का एक ही ओनर हो, और हर write path retry होने या किसी भी stack द्वारा चलने पर सुरक्षित हो।

Rules नियम

  • Migration ownership: migrations run as a single CI/release step, never from application start-up on either stack. Guard with an advisory lock so two runners can never overlap. Migration ownership: migrations एक ही CI/release चरण के रूप में चलें, किसी भी stack के application start-up से कभी नहीं। advisory lock लगाएँ ताकि दो runners कभी overlap न हों।
  • Backward-compatible (expand/contract): add nullable columns or new tables first; deploy code that works with old and new; backfill; only much later (after the rollback window) drop old columns. Never rename or drop in the same release. Backward-compatible (expand/contract): पहले nullable columns या नई tables जोड़ें; ऐसा code deploy करें जो पुराने और नए दोनों के साथ चले; backfill करें; बहुत बाद में (रोलबैक विंडो के बाद) पुराने columns हटाएँ। एक ही release में rename या drop कभी नहीं।
  • Idempotency: for payments, emails, webhooks and "create" APIs use a client/request idempotency key with a unique constraint and INSERT ... ON CONFLICT DO NOTHING. Idempotency: payments, emails, webhooks और "create" APIs के लिए unique constraint वाली client/request idempotency key और INSERT ... ON CONFLICT DO NOTHING इस्तेमाल करें।
  • Connections: keep the total pool budget under the Phase 2 limit; set statement and idle-in-transaction timeouts so a stuck request cannot hold locks. Connections: कुल pool budget फ़ेज़ 2 की सीमा के नीचे रखें; statement और idle-in-transaction timeouts सेट करें ताकि अटका request locks न पकड़े।
  • No manual writes to production tables during the migration except through reviewed, backed-up scripts. माइग्रेशन के दौरान प्रोडक्शन tables में कोई manual writes नहीं, सिर्फ़ reviewed और backed-up scripts के ज़रिए।
Honest limits of rollback रोलबैक की ईमानदार सीमाएँ

Moving traffic back to App Runner does not revert rows written by EC2. A restore from snapshot or PITR always goes to a new instance, and then you must reconcile the data written since the restore point; cutting production back to a restored copy loses writes made after that moment. Treat data repair as an incident procedure with the DBA, not as a rollback button. ट्रैफ़िक App Runner पर लौटाने से EC2 द्वारा लिखी rows वापस नहीं होतीं। snapshot या PITR से restore हमेशा नए instance पर होता है, और फिर restore point के बाद लिखे डेटा का मिलान करना पड़ता है; प्रोडक्शन को restored कॉपी पर ले जाने से उस क्षण के बाद की writes खो जाती हैं। डेटा repair को DBA के साथ incident प्रक्रिया मानें, रोलबैक बटन नहीं।

Rollback moves requests, not data. रोलबैक requests हटाता है, डेटा नहीं।

  1. Declare the incident; name the incident commander. Pause any deploy and any traffic increase. incident घोषित करें; incident commander नामित करें। हर deploy और ट्रैफ़िक बढ़ोतरी रोकें।
  2. Traffic rollback: apply the prepared change batch (App Runner weight 100, EC2 weight 0). Section 17 / 27. Traffic rollback: तैयार change batch लागू करें (App Runner weight 100, EC2 weight 0)। सेक्शन 17 / 27।
  3. Worker ownership: if it was handed to EC2, hand it back to App Runner (or confirm the leader lock). Check queue depth falls. Worker ownership: यदि EC2 को दी गई थी तो App Runner को वापस दें (या leader lock की पुष्टि करें)। queue depth घटती है यह देखें।
